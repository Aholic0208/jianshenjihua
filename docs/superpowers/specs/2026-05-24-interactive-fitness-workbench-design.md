# 交互式健身计划工作台设计

## 目标

把当前“多页面展示 + 规则样例”的 MVP 升级成一个真实可用的健身计划产品：用户完成分步建档后，进入一个统一的计划工作台，在同一套交互里完成切周、查看每日训练与饮食、点动作看教学、提交打卡、请求调整，并得到真正因个人情况而变化的计划结果。

## 适用人群与边界

- 仅服务 18 岁以上普通成年人。
- 第一阶段覆盖的核心目标：减脂、塑形、基础增肌、体态改善。
- 第一阶段不为孕期、术后、急性疼痛、严重慢性病、极端减重目标用户生成激进计划；此类情况只输出保守提示与转诊建议。
- 产品定位是一般健身辅助，不替代医生、营养师或持证教练的诊断与处方。

## 产品形态

第一阶段产品是一个本地可运行的响应式 Web 应用，桌面和手机浏览器都可使用。用户进入后不是来回跳多个孤立页面，而是经历两个核心场景：

1. 分步建档向导
2. 计划工作台

工作台是整个产品中心。用户从这里看周计划、打开动作详情、完成打卡、发起调整、查看历史版本和个人资料。

## 核心交互

### 1. 分步建档向导

建档向导使用连续的多步骤交互，而不是普通长表单。步骤如下：

1. 基础信息：年龄、性别、身高、体重、目标体重
2. 目标与训练场景：目标类型、每周训练天数、单次时长、居家/健身房/混合
3. 器械与经验：器械条件、训练经验
4. 限制条件：伤病、慢性病、疼痛、过敏、饮食限制、预算、睡眠
5. AI 追问确认：系统根据缺失项或风险点提出 2-4 个补充问题
6. 生成计划：展示“正在生成你的 4 周计划”

要求：

- 允许上一步/下一步
- 自动保存草稿
- 中断后可恢复
- 风险输入在向导中即时提示，不等到最后才报错

### 2. 计划工作台

工作台是一个统一视图，不再让用户在多个页面之间迷失。核心结构：

- 顶部：计划状态、当前用户、主导航
- 左侧/顶部摘要区：身体数据、训练边界、风险状态、当前计划版本
- 中间主区域：
  - 周切换（第 1-4 周）
  - 一周 7 天计划视图
  - 选中某一天后的“今日详情”
- 右侧/底部辅助区：
  - 打卡模块
  - 调整模块
  - 最近反馈和系统修订

在桌面端使用“三栏工作台”或“两栏 + 详情区”的结构；移动端折叠为单列，但保持周切换、当日详情和动作详情抽屉。

### 3. 动作详情

点击任意训练动作时，不强制整页跳转。第一阶段推荐：

- 桌面端：右侧抽屉
- 移动端：底部弹层/全屏抽屉

动作详情需要包含：

- 标准动作图示
- 动作步骤
- 发力要点
- 常见错误
- 哪些情况不适合
- 替代动作
- 视频演示入口

### 4. 打卡与计划调整

打卡和调整要直接作用于当前计划，而不是只留下文字记录。

打卡内容至少包括：

- 是否完成
- 体重（可选）
- 疲劳
- 疼痛
- 饥饿感
- 备注

调整内容至少覆盖三类：

- 动作替换
- 训练降载/增载
- 饮食替换

系统接到反馈后，需要：

1. 判断反馈类型
2. 给出替代或修订建议
3. 保存修订记录
4. 反映到当前天或当前周计划中

## 动作媒体系统

第一阶段不追求动作库数量，而追求少量动作的专业完整度。首批覆盖核心动作：

- 原地抬腿热身 / 快走热身
- 徒手深蹲
- 臀桥
- 上斜俯卧撑
- 哑铃划船 / 弹力带划船
- 平板支撑
- 跑步机快走 / 快走有氧
- 基础拉伸

每个动作需要：

- 高质量标准动作图
- 高质量常见错误图（至少关键动作覆盖）
- 图文注意事项
- 替代动作说明
- 视频链接字段

第一阶段视频采用高质量外部教学视频链接，站内保留可直接播放或跳转的结构。后续可替换为站内自有视频。

图片质量必须从“装饰示意图”升级为“教学图”。图像风格必须统一、清晰、解剖姿态正确、背景干净，避免艺术化和误导性姿势。

## 计划生成策略

第一阶段计划生成采用“规则引擎为主，AI 解释为辅”。

### 规则引擎负责

- 风险筛查
- 训练频率
- 每日训练类型分布
- 动作难度选择
- 动作禁用与替代
- 热量目标与蛋白质目标
- 基础饮食建议和食物替换

### AI 负责

- 对缺失信息做补充追问
- 生成更自然的解释和摘要
- 把结构化计划转化为更易理解的用户语言
- 在调整场景里生成更贴近语境的建议文案

### 个性化输入影响输出

- 目标类型：改变训练结构与营养方向
- 训练场景：改变动作来源
- 训练经验：改变动作复杂度、训练量、提示密度
- 伤病/疼痛：改变动作白名单、黑名单和替代逻辑
- 饮食限制/过敏/预算/睡眠：改变三餐与替换建议

## 专业边界与参考

第一阶段的训练与健康边界参考公共卫生与营养官方建议，不直接仿写私人教练口径。计划生成需要体现这些保守边界：

- 成人每周至少 150 分钟中等强度活动，或等效 75 分钟高强度活动，并进行每周至少 2 天的肌力训练。[CDC](https://www.cdc.gov/physical-activity-basics/guidelines/adults.html)
- WHO 对成年人给出的活动量建议与“从小剂量逐步增加”的原则保持一致。[WHO](https://www.who.int/health-topics/noncommunicable-diseases/physical-activity)
- 减重速度控制在合理保守范围，优先避免极端热量缺口；NHLBI 给出的常见建议是每周约 1-2 磅，并通过日均约 500-750 kcal 缺口支持减重。[NHLBI 1](https://www.nhlbi.nih.gov/health/educational/lose_wt/control.htm) [NHLBI 2](https://www.nhlbi.nih.gov/health/educational/lose_wt/eat/calories.htm)
- 饮食建议以健康膳食模式为基础，而不是极端饮食法；遵循《Dietary Guidelines for Americans》倡导的健康饮食模式、食物组平衡与卡路里范围。[Dietary Guidelines](https://www.dietaryguidelines.gov/sites/default/files/2020-12/Dietary_Guidelines_for_Americans_2020-2025.pdf)

## 后端结构

第一阶段延续 Next.js + TypeScript + SQLite，但重构为更清晰的结构：

- UI 层：向导、工作台、动作详情、打卡、调整
- Action/API 层：保存建档、生成计划、获取周计划、打卡、调整、动作详情
- Plan Engine：风险筛查、训练模板、营养目标、替代逻辑、调整逻辑
- Repository：用户、评估、计划版本、周/日计划、打卡、调整、媒体

## 数据结构方向

在现有数据模型基础上增强这些概念：

- `users`
- `assessments`
- `plans`
- `plan_weeks`
- `plan_days`
- `workout_items`
- `nutrition_days`
- `check_ins`
- `adjustment_requests`
- `plan_revisions`
- `exercise_media`

即使底层仍有 JSON 存储，业务层也要呈现出这些结构，而不是把所有内容挤在一个页面级对象里。

## 测试策略

第一阶段至少覆盖：

- 多步骤建档流程
- 因不同输入而变化的计划结构
- 切换第 1-4 周显示不同周内容
- 选中某一天后展示对应训练与饮食
- 动作详情显示教学字段
- 打卡后更新当前状态
- 调整后生成修订记录并更新当前计划
- 高风险输入时触发限制逻辑

## 第一阶段完成标准

如果一个普通成年新手打开产品并完成建档，他应该能：

1. 顺利完成分步输入
2. 进入一个统一工作台
3. 切换第 1-4 周
4. 查看某一天要做什么、吃什么
5. 点击动作看清楚标准做法、常见错误和注意事项
6. 完成今日打卡
7. 说出“太累/做不到/膝盖不舒服/吃不了这个”并看到计划变化

如果这 7 件事做到了，第一阶段就算达标。否则再漂亮也不算完成。
